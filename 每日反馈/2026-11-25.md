## 学到的知识点

### 一、`freejoint` 是一个词，不能拆

```xml
<free joint/>        <!-- 错：报 XML parse error -->
<freejoint/>         <!-- 对 -->
```

`<free joint/>` 会被当成一个叫 `free` 的元素加 `joint` 属性，整个模型建不起来。

同样容易错的两个：

- `<joint ...>` 忘写 `/>` —— 实测报 `XML parse error 14`
- 注释里把 `fromto` 拼成 `fromoto` —— 不报错但会误导以后照着抄

### 二、nq 和 nv：位置用几个数，自由度有几个

本机实测四类关节：

| 关节 | nq | nv | 原因 |
|---|---|---|---|
| hinge 单摆 | 1 | 1 | 一个角度 |
| slide 滑轨 | 1 | 1 | 一个位移 |
| ball 球窝 | 4 | 3 | 姿态用四元数（4 个数）记 3 个转动 |
| freejoint 自由方块 | 7 | 6 | 3 位置 + 4 姿态；速度 3 平动 + 3 转动 |

**差距只在姿态上**：转动自由度是 3，但为了避开欧拉角的万向节死锁，用 4 个数（四元数）记。所以 `qpos` 有 7 个，`qvel` 只有 6 个。

### 三、力矩：力 × 力臂

`tau = 力 × 力臂`，单位 N·m。同样的力，离转轴越远力矩越大（开门的把手为什么在最外侧）。

实测这条 1 kg、0.5 m 的腿：

```
角度 0 rad（竖直）  -> 重力力矩 0 N·m（自然平衡，不用电机）
角度 0.5 rad        -> 需要 1.18 N·m 才能保持住
角度 1.0 rad        -> 需要 2.06 N·m
ctrl = 1 N·m        -> 角加速度 11.485 rad/s^2
```

**“保持一个姿势不动”的代价，就是电机要一直对抗重力力矩。**

### 四、PD 控制：两个项各解决一个问题

```python
err = (TARGET - q + np.pi) % (2*np.pi) - np.pi   # 折到 [-pi, pi]
data.ctrl[0] = np.clip(KP * err - KD * qd, -50, 50)
```

- **P 项（KP × 误差）**：差得远就推得狠，负责“到得了”
- **D 项（- KD × 角速度）**：越快刹车越狠，负责“停得下”

实测（KP=80，目标 π）：

| KD | 轨迹（每 0.2 秒角度） | 结果 |
|---|---|---|
| 8 | 0 → 2.65 → 3.09 → 3.14 | 0.6 秒到位，无超调 |
| 2 | 0 → 4.33（冲过 69°）→ 2.82 → 3.14 | 超调一次 |
| 0 | 0 → 1.81 → 3.96 → 5.58 → 6.26…… | 永远振荡，停不下来 |

**另一个必须知道的坑**：KP=80 时初始力矩 80×π=251 N·m，但 `ctrlrange` 只允许 50，所以误差超过 50/80=0.625 弧度（36°）时，电机一直满功率输出。这叫力矩饱和。

### 五、角度归一化：不是可选项

关节没有限位，`qpos` 会无限增长。直接相减会算错：

```
TARGET = π, q = 7.0（已转一圈多）
直接相减：π - 7.0 = -3.858        ← 超出 [-π, π]，错
归一化后：2.425                    ← 正确，还差 2.425 弧度
```

`(x + π) % (2π) - π` 就是角度回绕（wrap），保证永远算“最近的那条路”。

### 六、timestep 决定每步多久，不决定控制器好坏

同样跑到 -170 度（实测）：

```
dt = 0.002  -> 146 步，0.292 秒
dt = 0.001  -> 291 步，0.291 秒
dt = 0.0005 -> 581 步，0.290 秒
```

**步数翻倍，物理时间不变。** PD 公式里没有 dt，所以控制器表现由物理时间决定，不由步数决定。

但步长太大会炸：`dt = 0.05` 时实测冲到 -206 度、来回振荡。

### 七、MuJoCo 的被动性：这是理解控制的关键

物理引擎不会自己动。它每 0.002 秒问一次“这个关节给多少力”，你给 0 它就按 0 算。

所以控制不是“解一个方程求最优力”，而是**每秒 500 次重复“看差距 → 推一把 → 引擎走一小步”**。前 50 步误差还接近 π，力矩一直是 -50；转到 -90° 时误差变小，力矩自动降到 19.8；转到 -177° 时只剩 0.69。

**推力变小，是因为误差变小——这是负反馈，不是查表。**

### 八、viewer：播放速度和仿真速度是两回事

```python
with mujoco.viewer.launch_passive(model, data) as viewer:
    while viewer.is_running():
        ...
        mujoco.mj_step(model, data)
        viewer.sync()
        time.sleep(1 / 240)
```

- `launch_passive`：仿真循环归你管，viewer 只负责画
- `sync()`：把最新状态推给窗口
- `sleep`：控制**播放速度**。每帧 1 步物理（2 ms）却 sleep 4.17 ms，所以画面比实时慢一半（0.48 倍）

## 心得

### 1. “系统不会自己动”这句话改变了看代码的方式

以前看 `for` 循环，觉得是“重复执行同一件事”。现在看成**每一拍重新做一次决定**——读状态、算误差、出力、推进，500 次/秒。

理解了这一点，才明白为什么不能“开头算一次力然后让它跑”；也因为这样，PD 那两个参数才不再是抽象的字母，而是“油门”和“刹车”。

### 2. 错误分两类，排查方式完全不同

- **语法/结构错误**：XML 没闭合、`mj_step(model.data)`、`20. 50`——当场报错，改掉就好
- **物理/参数错误**：`ctrlrange` 给到 ±50 但腿只需要 3 N·m、不加阻尼导致永远摆动——不报错，跑起来才看出来

第二类更难发现，因为它“能跑”。以后写完先问一句：**这些数字的量级合理吗？**
